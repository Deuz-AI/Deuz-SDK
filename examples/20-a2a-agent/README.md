# 20 — A2A agent

**Shows:** a native agent run served over the Agent2Agent protocol (A2A 1.0) with `createA2AHandler` and `createA2AAgentExecutor` (2.3), and an A2A client in the same process. The client discovers the agent's card and streams a booking request; the run calls a `needsApproval` tool and suspends, so the task turns `INPUT_REQUIRED` with the pending approval in a `pending-actions` data part. An answer that does not fit (text alone) is refused with `INVALID_PARAMS` and changes nothing. The client then answers the approval in a data part, the run resumes, and its validated, typed output arrives as the task's `booking` artifact. The task id is the native run's id.

**Run:** from the repo root, `npm install && npm run build`, then `npm run dev -w @deuz-examples/20-a2a-agent`. No API key and no network needed: the client's `fetch` calls the handler directly. Node ≥ 22.6 for the type stripping.

**Real provider:** the model is `createMockModel` from `@deuz-sdk/core/testing`, scripted one reply per call. Replace it with `createAnthropic({ apiKey: process.env.ANTHROPIC_API_KEY })('claude-opus-4-8')` from `@deuz-sdk/core/anthropic` (see the `REAL PROVIDER` comment in `index.ts`). To serve the agent for real, hand every request to `handler` from a fetch-style server (Workers, Deno, Bun, a route handler), put its public URL in the card, and drop `deps: { fetch }` from the client, which then calls the agent over the network. The handler checks the protocol, not the caller, so authenticate every request in front of it (and answer browser CORS preflights there), and name the verified caller with `owner` on `createA2AHandler`, for example `owner: async (request) => (await verifySession(request))?.userId`. Without it every caller shares the tasks, whose runs live under the scope `["a2a",null,null]` (step 4): anyone who learns a task id can read the task, cancel it or approve its `bookTable` call. With it, each caller reaches only its own tasks, given a task store that keys tasks by scope, as the default one does (see [tasks, tenants and owners](../../docs/content/docs/modules/a2a.mdx)).

**Look at:** the approval travels as data, not prose: each pending action names its `kind`, tool, input and `approvalId` (and the `token` of a signed approval), and the answer uses the names `resumeAgent` takes, every action in one message. Only a completed run stores an artifact, and only its validated output. For tasks and runs that survive a restart or span instances, use durable stores (an `A2ATaskStore` for the tasks and, for example, `createSqliteOpsStore({ path }).agentRuns` from `@deuz-sdk/core/ops/sqlite` for the runs) and pass `lease` to `createA2AAgentExecutor`.
