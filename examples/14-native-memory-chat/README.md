# 14 — Native memory and chat

**Shows:** a native run (2.3) with `memory`, `chat` and `fallbackModels`, over two runs in one chat. The first run recalls nothing (nothing is stored yet), completes, and only then is extracted: the memory model finds one fact, written with the run's id in `metadata.deuz`. The second run continues `chat-1` and recalls that fact **once**, before its first model call, as an appended `role: 'system'` message. Its three model calls (the one that failed, a tool step and the answer) all send that message, and the memory store is searched once. In both runs the primary's provider answers 503, so the call goes to the fallback model inside the same run: the checkpoint records the fail-over (`AgentRunEnvelope.models`), and the failed model is skipped for the rest of the run. When the second run ends, the chat database is down. The run still completes, streams a `warning` part (`setting: 'chat'`) and records its projection as `failed`; `reconcileAgentRun` writes it once the database is back, and a second pass finds nothing behind (`'current'`).

**Run:** from the repo root, `npm install && npm run build`, then `npm run dev -w @deuz-examples/14-native-memory-chat`. No API key needed; Node ≥ 22.6 for the type stripping.

**Real provider:** the fallback and the memory model are `createMockModel` from `@deuz-sdk/core/testing`, scripted one reply per call. The primary is an OpenAI model whose injected `fetch` answers every request with a 503 itself, so nothing reaches the network. Replace the three models with real ones (see the `REAL PROVIDER` comment in `index.ts`); the memory model can be a smaller one. The 503 follows OpenAI's documented error shape; how a provider fails during a real outage is not live-verified.

**Look at:** the run's checkpoint (`runs.load(runId)`) is the canonical record, and it says what happened to each part: `memory.recall` (`recalled`, its index and count), `memory.extraction` (written as `pending` with the terminal commit, then `completed` with its mutation count), `models` (each fail-over and the model the run calls now) and `chat` (its status, how many transcript messages the chat store acknowledged, the message ids). In `ChatRecord.messageIds` an input message keeps the id the stored chat gave it (`ada-1:0`) and a turn of a run is `<runId>:<n>`; every save replaces the whole record, so a repeat never appends a message twice. The recall message is part of the projection, so the next run replays the exact prefix the model saw. Memory, chat and `fallbackModels` are part of the resume binding: a resume with another scope, chat or fallback list fails before anything is written. A run without a `session` still recalls, extracts and writes its projection, but leaves no record to resume or reconcile. `reconcileAgentRun({ session, chat, memory })` also settles an extraction an interruption left `pending`; call it only when no executor drives the run, or pass `lease`. For a store that survives restarts, pass `createSqliteOpsStore({ path }).agentRuns` from `@deuz-sdk/core/ops/sqlite` instead of `createInMemoryAgentRunStore()`.
