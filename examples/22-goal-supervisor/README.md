# 22 — Goal supervisor

**Shows:** a durable goal driven from a schedule to a verified result with `@deuz-sdk/core/goal/runtime` (preview), on one SQLite file. The goal: no dependency of `acme/api` has a known vulnerability. Its criterion passes only on the host verifier's verdict about an audit report.

1. Thursday, host A: `createGoalSupervisor(...).submit` creates the goal with its runtime state (`start: false`, so no run starts yet). A `wait` command makes it wait for an event from the schedule `weekly-audit`. `createDurableScheduler(...).put` adds that schedule: Mondays 09:00 in `Europe/Berlin`, which is 07:00 UTC on 19 October and 08:00 UTC on 26 October, after the clocks go back. Nothing is due, so neither tick does anything. Host A closes its connections.
2. Monday 09:25 Berlin time, host B opens the same file. It was down at 09:00, so its first scheduler tick finds the occurrence past the 60 s grace and catches it up under the default `catchUp: 'latest'`. The schedule cursor and the inbox delivery are committed together, so a second tick finds nothing. The supervisor tick claims the goal under its goal lease and applies the inbox entry. The goal becomes active, and the supervisor records a start intent for run `deps-clean:run:1` in the same transaction. The native launcher starts the run as a V3 run (`checkpointVersion: 3`). The run audits (two vulnerable packages) and asks to upgrade them. The upgrade needs an approval, so the run suspends and the goal waits for the host (`user`, note `approval`).
3. The on-call engineer approves. The host reads the pending approval from the run's V3 record and calls `supervisor.resume` with the verdict, which is stored with a resume intent. The next tick resumes the same run: the upgrade runs, a second audit is clean and the run completes. The `verify` hook calls `verifyGoalAcceptance`. It checks the report the run filed with the host's `GoalVerifier` (`dependency-audit@1`), re-reads the report's digest before and after the check, and returns the `evaluate` command. The criterion passes, so the goal completes (`accepted`). The run's usage is charged to the goal's budget once (four mock calls of 15 tokens each).
4. The goal is done, so the host cancels the schedule. The next Monday's tick delivers nothing. The only occurrence record is the one delivered on 19 October.

**Run:** from the repo root, `npm install && npm run build`, then `npm run dev -w @deuz-examples/22-goal-supervisor` (or `npm start` in this folder). No API key needed. It needs Node ≥ 22.6 for the type stripping, and `node:sqlite`, which ships unflagged from Node 22.13 and 23.4. The SQLite file lives in a temporary directory that the example removes at the end.

**Real provider:** the model is `createMockModel` from `@deuz-sdk/core/testing`, scripted one reply per call across both legs of the run. Replace it with `createAnthropic({ apiKey: process.env.ANTHROPIC_API_KEY })('claude-opus-4-8')` from `@deuz-sdk/core/anthropic` (see the `REAL PROVIDER` comment in `index.ts`). A real model chooses its own tool calls. If it ends without filing a report, the `verify` hook parks the goal for a person instead of completing it. Every leg is charged to the goal's budget of 20 000 tokens, so raise the budget if your runs use more.

**Look at:** the scheduler and the supervisor are library loops in your process, not a service. Here each step is one `tick()` on a clock moved by hand, so the output is the same on every run. In production, call `start()` on each, and they tick every `pollMs` (1 s by default) on the injected clock. The two hosts stand in for one process before and after a restart. Each opens its own connections, and nothing passes between them except the file: the goal, its wait, the schedule cursor, the inbox, the run intents and the V3 run record are all durable there. Several processes can share the file, since the SQLite goal runtime store runs each write in one `BEGIN IMMEDIATE` transaction. The lease decides only who works on a goal now. Every write is still a revision compare-and-set, so a supervisor that lost its lease cannot overwrite a newer state. A run that suspends, or that stops or fails for good, parks the goal for the host (a drained run is resumed later, and a failure the native layer marks retryable is retried up to three times). The supervisor never starts a new run on its own then, because a new run could repeat an outside effect. Completion rests on the verifier's verdict about the report's digest, never on what the model says. PostgreSQL versions of the stores are `createPostgresGoalRuntimeStore` from `@deuz-sdk/core/goal/runtime/postgres` and `createPostgresAgentRunStoreV3` from `@deuz-sdk/core/ops/postgres`.
