# 15 — Native UI bridge

**Shows:** the 2.3 native UI bridge without a framework. A route function, `POST(request)`, starts a native run with `streamAgent`, or resumes the run a request names (`runId`) with `resumeStreamAgent`, and serves it with `toDeuzAgentStreamResponse`, journaled in a `StreamStateStore` under the run id. The client half, in the same process, calls the route with a `Request`, reads the `Response` body with `readDeuzStream`, folds the `data-agent` frames into the run's state with `agentStateFromParts`, and folds every part into the assistant turn with `applyUIPart`. The run asks for a gated `refund`: the first response ends with the run `suspended`, and its pending approval becomes the client's pending action. The client approves, and one request with `runId` and `approvalResponses` resumes the run: the tool runs on the server, the finalization streams drafts of the output, and the terminal frame delivers the validated output, typed as `Receipt`. Another tab then replays the run's journal: folded from nothing it gives the same terminal state, and folded into the state the first client holds it changes nothing.

**Run:** from the repo root, `npm install && npm run build`, then `npm run dev -w @deuz-examples/15-native-ui-bridge`. No API key needed; Node ≥ 22.6 for the type stripping. No framework or server process either: the client calls the route function directly, the way a framework would.

**Real provider:** the model is `createMockModel` from `@deuz-sdk/core/testing`, scripted one reply per call. Replace it with `createAnthropic({ apiKey: process.env.ANTHROPIC_API_KEY })('claude-opus-4-8')` from `@deuz-sdk/core/anthropic` (see the `REAL PROVIDER` comment in `index.ts`); the rest of the file stays as it is.

**Look at:** each frame's `seq` is its SSE event id, and because both legs are journaled under one `streamId`, the resume numbers on from the first response, so the run's state never moves backwards and a replay that overlaps what a client holds applies nothing twice. A draft (`partial`) is `unknown`, never a `Receipt`; only the `completed` state has an `output`, the value the server validated. The finalization also streams its candidate JSON as text, so the client takes the output from the agent state, not from the turn's text. `resumeStreamAgent` goes on only with a verdict for every pending approval and a result for every pending client call, so one request carries them all; the route refuses another tenant's run (404) and a run that is not waiting (409) before a leg starts. Nothing private leaves the server: no transcript, no raw tool results, no receipts, no ledger. The agent frames are wire v2 parts, so a client that asks for v1 (`x-deuz-stream: v1`) gets the plain chat stream. In a React app, `useChat` from `@deuz-sdk/react` does this client's work against the same route; the frozen `@deuz-sdk/core/react` hook does not read agent frames. In production, keep the runs in a durable store (`createSqliteOpsStore({ path }).agentRuns` from `@deuz-sdk/core/ops/sqlite`), the journal in a store every instance shares, take the scope from authentication, and serve `resumeDeuzStreamResponse(streams, runId, { lastEventId })` from a GET route so a client that lost its connection resumes after its cursor.
