# 18 — Batch requests, offline

**Shows:** the 2.3 batch module, `@deuz-sdk/core/batch`, on a scripted stand-in for Anthropic's Message Batches API. `createBatchClient` binds one model (`claude-sonnet-5-5`) and a run's execution context (`budget: { usd: 0.05 }`). `submit` sends three structured requests that triage support tickets, and each one first reserves a hold in the run's ledger: the prompt estimate plus the `maxOutputTokens` the wire sends, priced at the model's batch rates. `wait` polls until the batch ends (`onStatus` prints each poll), and `results` reads one result per request and settles its hold before handing the result out: the two that succeeded settle at batch rates (the standard price is printed next to them), and the one that expired is released, because it never ran and was never billed. A second batch on `claude-sonnet-4-5`, which has a standard price but no batch price, still runs: the job carries an `unpriced-model` warning, its hold counts tokens but no dollars, and `collect` gathers its results. `[api]` lines are the calls the client made.

**Run:** from the repo root, `npm install && npm run build`, then `npm run dev -w @deuz-examples/18-batch-offline`. No API key and no network: the API is the model's `fetch`. Node ≥ 22.6 for the type stripping.

**Real provider:** drop `fetch: scriptedApi` and pass a key, `createAnthropic({ apiKey: process.env.ANTHROPIC_API_KEY })` (see the `REAL PROVIDER` comment in `index.ts`), and poll at a real pace: `wait` checks every 60 seconds by default, and a batch can take up to 24 hours. OpenAI models (`createOpenAIResponses` from `@deuz-sdk/core/openai`) and Gemini models (`createGoogleNative` from `@deuz-sdk/core/google`) batch through the same client; the bundled price table has no batch price for them, so their batch requests are unpriced until you add a `batch` card to their row (`createPriceProvider({ table })`). None of the three batch APIs is live-verified: the shapes come from the providers' official SDK types, so submit a small batch before you rely on a large one.

**Look at:** the holds are admitted all or none when the batch is submitted: if one request does not fit the budget, the holds admitted before it are released and nothing is sent. How a result closes its hold: settled with the usage when the request succeeded; released when it was cancelled or expired, or refused with 400, 401, 403, 404, 422 or 429; kept as unknown for any other error, because it may have been billed. Settlement is idempotent, so reading the results again changes nothing and an interrupted read can start over. A hold can stay open as long as the batch (`holdMs`, 25 hours by default, recorded as `job.holdUntil`), so a `BudgetStore` sweep must not close batch holds before that. With `budget.unknownPrice: 'reject'`, the second batch would be refused before anything is sent. The `BatchJob` is plain JSON without credentials: give the client a `store` (`createMemoryBatchJobStore()` or your own `BatchJobStore`) and another process can list the open jobs with `pending()` and read their results, settling the holds through an execution context restored from the run's snapshot or created with the same scope.
