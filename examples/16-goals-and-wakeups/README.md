# 16 — Goals and wakeups

**Shows:** the 2.3 goal contract, `@deuz-sdk/core/goal`, driven by two workers that share one SQLite ops file. The goal `links-fixed` is done only when its criterion, "the link checker finds no broken link", passes on evidence. It begins by waiting for a wakeup tied to the schedule `nightly-links` (02:00 UTC). Both workers tick that minute with `createScheduler`, and the ops store's durable `claims` gives the occurrence to one of them; the other reports a duplicate. The occurrence's event (`goalEventFromOccurrence`, keyed `nightly-links@<at>`) wakes the goal, and the worker starts one native run for it, holding the run's lease (`lease: { provider: ops.leases }`). During that run's tool call, the other worker's recovery sweep finds the run looking stale (`findStaleAgentRuns`) and tries to resume it; the lease refuses it with `lease_held`. The run's usage becomes a charge on the goal and its tool's report the evidence: three broken links, so the criterion fails and the goal waits for an outside event, the next docs deploy. The deploy webhook's event (`goalEventFromSignal`, keyed by the delivery id, claimed in the same key space) wakes the goal again; a second run finds no broken link, the criterion passes on that tool evidence, and the goal completes. The sender's retry of the delivery is a duplicate, and the ended goal ignores the next night's occurrence.

**Run:** from the repo root, `npm install && npm run build`, then `npm run dev -w @deuz-examples/16-goals-and-wakeups`. No API key needed. It needs Node ≥ 22.6 for the type stripping, and `node:sqlite`, which ships unflagged from Node 22.13 and 23.4. The SQLite file lives in a temporary directory that the example removes at the end.

**Real provider:** the model is `createMockModel` from `@deuz-sdk/core/testing`, scripted one reply per call across both runs. Replace it with `createAnthropic({ apiKey: process.env.ANTHROPIC_API_KEY })('claude-opus-4-8')` from `@deuz-sdk/core/anthropic` (see the `REAL PROVIDER` comment in `index.ts`).

**Look at:** nothing in `@deuz-sdk/core/goal` runs by itself. Every change is a `transitionGoal(record, command, { now })` that a worker saves, and the time is the worker's: here it is moved by hand, so the output is the same on every run. A running supervisor, a durable inbox and timezone-aware wakeups are planned for 2.4. Two layers dedupe: the durable claim keeps a second worker from acting on an occurrence or a delivery at all, and the goal remembers the keys of the last events it applied (`seen`), so an event that reaches it twice is ignored as a duplicate. Each write is a load, transition and save: the goal store saves only the stored revision plus one, so of two workers that save at once, one wins and the other loads again. The lease holds the run, not the occurrence: its key is `agentRunLeaseKey({ scope, runId })`, and while the executor lives, a resume elsewhere fails before it reads or writes anything; once the executor dies and its lease lapses, the sweep takes the run over. A native run saves at every step, not on a heartbeat, so a run in a long tool call looks stale too (the sweep's clock is moved ahead here instead of waiting). Acceptance rests on the checker's report (`source: 'tool'`); a verdict from the working model (`source: 'model'`) would be recorded as inconclusive. `createInMemoryGoalStore` stands in for a table of your own that both workers share.
