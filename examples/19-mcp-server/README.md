# 19 — MCP server

**Shows:** the 2.3 MCP server, `@deuz-sdk/core/mcp/server`. `createMcpServer` publishes two Deuz tools, `lookup_order` and `refund_order` (marked `needsApproval`), and an agent, `support_agent`: a whole `runAgent` behind a tool that takes `{ prompt }`. `server.ready()` loads the MCP SDK and prepares every tool before the first request. The Deuz MCP client connects in this process, because its `transport.fetch` is `server.fetch`: no socket, no port. With the official v2 MCP packages installed, the client runs on the v2 SDK line and negotiates MCP 2026-07-28. `listTools()` returns the served tools as a `ToolSet`; `callTool` gets a structured result back as the value, and a tool that throws comes back as an error result, which the client throws with the tool's message. Each refund asks the client's user first, through an MCP elicitation that the client answers in `onElicitationRequest` (scripted here): accepted, the refund runs; declined, the call is denied and the tool never runs. The agent call runs a whole native run on the server, the agent's own tool call included, and the client receives its final answer.

**Run:** from the repo root, `npm install && npm run build`, then `npm run dev -w @deuz-examples/19-mcp-server`. No API key and no network. The example depends on `@modelcontextprotocol/server` and `@modelcontextprotocol/client`, the v2 MCP SDK (optional peers of `@deuz-sdk/core`, imported only when used; they bring their own Zod 4). Node ≥ 22.6 for the type stripping.

**Real provider:** the agent's model is `createMockModel` from `@deuz-sdk/core/testing`, scripted one reply per model call. Replace it with `createAnthropic({ apiKey: process.env.ANTHROPIC_API_KEY })('claude-opus-4-8')` from `@deuz-sdk/core/anthropic` (see the `REAL PROVIDER` comment in `index.ts`); the tools and the server stay as they are. To serve real clients over HTTP, put `server.fetch` in a route handler (Workers, Deno, Bun, a Next.js route), then drop the client's `fetch` and point its `url` at the route. The handler does no Origin/Host validation or authentication of its own: put both in front of it and pass the verified identity as `server.fetch(request, { authInfo })`. To serve over stdio instead, run the server from a script of its own with `serveMcpStdio(server)` from `@deuz-sdk/core/mcp/server/stdio`; every byte on that process's stdout is protocol, so its tools must log to stderr (`console.error`), not to stdout as this example's `console.log` lines do. A stdio server is launched by its client: `createStdioMcpClient({ command: 'node', args: ['server.mjs'], onElicitationRequest })` from `@deuz-sdk/core/mcp/stdio` spawns it and talks over its stdin and stdout.

**Look at:** a served call runs the pipeline a loop call runs: the argument check, the tool guardrails, the approval gate, validation, `execute`. The default `approve: 'elicit'` takes the client's word for the user's answer; for clients you do not trust, decide on the server with `approve: (request) => …`. A client that cannot be asked is denied, never run: a client without `onElicitationRequest`, or one on the v1 SDK line, which speaks MCP 2025-11-25 and reaches this endpoint through its stateless fallback. The agent's usage stays on the server (MCP has no field for it). The server is verified offline against the Deuz client and the official SDK clients, not against hosted MCP clients.
