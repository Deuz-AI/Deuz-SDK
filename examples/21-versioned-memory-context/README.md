# 21 — Versioned memory and context

**Shows:** the 2.4 memory and context path in a V3 native run (`checkpointVersion: 3`).

1. The host remembers three things Ada said with `createMemorySession` from `@deuz-sdk/core/memory/versioned`. Each record has a stable id, revision 1, the origin `asserted` (only a host call asserts) and a source that cites her chat message by id and `sha256:` digest. Sending the same `operationId` with the same request again replays the stored receipt (`replayed: true`) and writes nothing.
2. A correction is a `revise` at `expectedRevision: 1`, which writes revision 2. A second writer that still expects revision 1 gets `RevisionConflictError` and nothing is written. `history` returns both revisions. `recall({ recordedAsOf })` returns what the store knew before the fix, and a plain `recall` returns the current revision.
3. A V3 run with `context: { sources: [createMemoryContextSource({ session })] }`, `workingMemory` (a host goal and constraint) and `versionedMemory: { session, tools: true }`. At step 0 the context compiler recalls and places the current revisions as one `<deuz_context>` block in the history. Each record in the block is labelled with its id, revision, origin and source kinds, and its text is escaped, so it reads as data and cannot pass for a host instruction. The working memory goes at the end of every request. At step 1 no refresh is due, so the step reuses the package (`refresh: reused`). The model calls `memory_remember`, and the write moves through `intended`, `committed` and `acknowledged` in the run record; the new record is `inferred` and cites the tool call. The run then waits for an approval of `schedule_deploy`.
4. The staging password should never have been stored. `forget` deletes the record's content, revisions and vectors; its receipts stay, without content. The session's `onForget` listener calls `runs.redactForgotten(event)`, which redacts the stored context package of step 0. The step 1 package held only the working memory and stays.
5. The approval resumes the run. Before its next request, the run drops the redacted block from its history and checkpoints. Step 2 is then compiled again from a fresh recall (`refresh: redacted`, `redacted: true`), without the forgotten record and with the one the model wrote. Afterwards the stored run record no longer contains the password, and the working memory never entered the history.

**Run:** from the repo root, `npm install && npm run build`, then `npm run dev -w @deuz-examples/21-versioned-memory-context` (or `npm start` in this folder). No API key needed; Node ≥ 22.6 for the type stripping. Everything lives in memory, so nothing is left behind.

**Real provider:** the model is `createMockModel` from `@deuz-sdk/core/testing`, scripted one reply per call. Replace it with `createAnthropic({ apiKey: process.env.ANTHROPIC_API_KEY })('claude-opus-4-8')` from `@deuz-sdk/core/anthropic` (see the `REAL PROVIDER` comment in `index.ts`). A real model decides on its own whether to call `memory_remember` and what to write, so the records and the steps can differ from this run.

**Look at:** nothing here runs unless you configure it. Without `checkpointVersion: 3`, a native run behaves as in 2.3 and refuses `context`, `workingMemory` and `versionedMemory`. The memory clock and ids are injected (`deps`), so the output is the same on every run. The session has no memory LLM, so writes are added as they are (`supersede: 'add'`). With an `llm`, `remember` reconciles new facts against similar records first. The manifest on each `context` event (and in `runs.load(runId).context.steps`) records ids, revisions, digests, token counts and the reason each candidate was selected or left out. It never holds the text itself. A `forget` changes what the SDK stores and what it sends from then on. It cannot take back what a provider already received in steps 0 and 1. It also leaves chats, the transcript index and your own files alone. For stores that survive a restart, use `createSqliteVersionedMemoryStore({ path })` from `@deuz-sdk/core/memory/versioned/sqlite` and `createSqliteAgentRunStoreV3({ path })` from `@deuz-sdk/core/ops/sqlite` (both also exist for PostgreSQL).
