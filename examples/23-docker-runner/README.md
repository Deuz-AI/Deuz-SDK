# 23 — Docker runner

**Shows:** the 2.4 local Docker sandbox and process runner from `@deuz-sdk/core/compute/docker` (preview, Node only), on alpine 3.20 pinned by digest.

1. `createDockerSandbox` implements the `ComputeSandbox` seam. Each `runShell` runs in a fresh container with the defaults: UID/GID 10001, `--network none`, 1 CPU, 512 MiB, 128 PIDs, every capability dropped, `no-new-privileges`, and no host directory or Docker socket mounted. The in-memory workspace is copied in through a size-limited archive. The command reads `orders.csv`, cannot reach the network, and writes `made.txt`, which never reaches the host workspace. A 1 s timeout kills a `sleep 30` (`timedOut: true`, exit `null`). A `cwd` outside the workspace is refused without running anything. With `maxOutputBytes: 64`, `seq 1 1000` comes back as its tail, marked `truncated`.
2. `createDockerProcessRunner` with a SQLite `ProcessOperationStore` runs a process in a fixed order: operation record, container create, staging of `orders.csv`, a durable `start-dispatched` record, one `docker start`, then inspection. The example polls until the process exits, reads its output tail, and reads `out/total.txt` as an artifact with its size and `sha256:` digest. A path that leaves the workspace (`../etc/passwd`) is refused with `artifact_rejected`.
3. The host "restarts": the store is closed and opened again from the same file, with a new runner. `start` with the same operation id and request finds the record and the same container, and does not start it again. The same id with another command throws `OperationConflictError` (`operation_conflict`).
4. `cancel` on a `sleep 300` is recorded first, then `docker stop` with a 2 s grace, then a kill. `sleep` runs as PID 1 and ignores SIGTERM, so the kill ends it.
5. `reconcile` matches the labelled containers of the run's scope with the store (no orphans, nothing lost). `dispose` removes both containers, and the stored output tail outlives them. `store.prune` then removes the finished records. Nothing is deleted in the background.

**Run:** start Docker, pull the image once (`docker pull alpine@sha256:d9e853e87e55526f6b2917df91a2115c36dd7c696a35be12163d44e6e2a4b6bc`; the SDK never pulls), then from the repo root `npm install && npm run build` and `npm run dev -w @deuz-examples/23-docker-runner` (or `npm start` in this folder). No API key needed. It needs Node ≥ 22.6 for the type stripping, and `node:sqlite`, which ships unflagged from Node 22.13 and 23.4. Set `DOCKER_PATH` when the Docker CLI is not on your `PATH`. Without a reachable Docker engine, or without the image, the example prints a skip message saying which and exits 0. The SQLite file lives in a temporary directory that the example removes at the end, and every container it starts is disposed.

**Real provider:** no model is involved. The sandbox implements `ComputeSandbox`, so `codeActTool(sandbox)` or `shellTool(sandbox)` from `@deuz-sdk/core/compute` hand it to a model the same way as the Node sandbox.

**Look at:** the module targets Linux containers. Docker Desktop runs them in a Linux VM; this example was run on Docker Desktop for Windows, and the SDK's required Docker tests run on Linux CI. Every container carries the labels `deuz.operation-id`, `deuz.scope` and `deuz.sdk-version`. Here the scope is `example-23-<pid>`, so `reconcile` only looks at this run's containers. Env values go through a private env file, never the command line. A process deadline (`deadlineAt`) is not durable (`durableTimeout: false`): nothing stops the container while the host is down, and a reconnect past the deadline cancels it. `readOnlyRootFilesystem: true` adds a read-only root with a bounded tmpfs `/tmp` (off by default, because some images write to their root). The writable layer can still fill the host's disk unless your storage driver supports `limits.storageBytes`. For one process, `createInMemoryProcessOperationStore()` records the operations instead of SQLite. There is no PostgreSQL store, because a container lives on one host's daemon.
