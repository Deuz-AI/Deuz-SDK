Native agent runs reach the UI. `toDeuzAgentStreamResponse(stream, options)` in `@deuz-sdk/core/ui` serializes a `streamAgent` or `resumeStreamAgent` run to the Deuz UI wire. The run's parts go out exactly as `toDeuzStreamResponse` frames them, and `data-agent` parts add what only a native run has: a `run` frame opening every leg (carrying the `runId` option), the phases, the `partial` drafts and validated array `element`s of a structured output, and a terminal `result` frame with the run id, the status, the validated output (only when `completed`), the pending approvals and client calls of a suspension, the stop reason with its `stopDetails`, or the failure. Every frame's `seq` is its own SSE event id. With `store` and `streamId` (one per run, such as the run id) the sequence grows across every leg, and a client resumes after its cursor through `resumeDeuzStreamResponse`; a response without a store cannot be replayed. The serializer subscribes to the run's events before it returns. It never sends the transcript, the raw result of a `tool-output` event, receipts or the accounting ledger, it redacts a failure's message, and it ends a failed run with an `error` part as well. The frames are wire v2 parts on the existing `data-${string}` member of `DeuzUIPart`, so a client that negotiated v1 gets the plain chat stream and no union is widened.

`agentStateFromParts(parts, initial?)` folds the frames into a `DeuzAgentState`: `idle`, `running` (with the latest unvalidated `partial` draft), `completed` (with `output: T`), `suspended`, `stopped` or `failed`. A frame applies only when its `seq` is above the state's, so a duplicate, a replay that overlaps the live stream or an out-of-order frame never applies twice, and the state never moves backwards. `applyUIPart` folds the same frames into the new optional `AssistantTurnState.agent`. An app's own `data-agent` part whose payload is no agent frame stays an ordinary data part.

The UI wire shows more of a turn. The `finish` and `step-finish` frames carry the provider's `stopDetails` (a refusal's category and explanation, secret-redacted), and `applyUIPart` keeps the `finish` frame's on the new optional `AssistantTurnState.stopDetails`. The `tool-state` and `tool-result` frames carry the dispatch contract's `outcome` (`ToolCallOutcome`), kept on the new optional `UIToolCall.outcome`; the latest frame wins, so a call that was `'approval-pending'` and then ran carries none. These optional fields ride every wire version, and an older client ignores them. Claude's thinking display modes need no new shape. Under `display: 'omitted'` a block stays an empty, signed reasoning part that adds nothing to the readable text and is sent back unchanged. Under `'updates'` (beta `thinking-display-updates-2026-08-18`, per `@anthropic-ai/sdk` 0.133.0's types) the progress notes are the block's text. Not live-verified. `readDeuzStream` gains `onEventId`, which receives each part's SSE event id right before the part is yielded.

A Gemini thought signature on a plain text part now rides the UI wire. The `text-delta` frame carries the text's `providerMetadata` (the signature often arrives on a final chunk whose text is empty), the UI text part keeps it, and `assistantMessageFromTurn` and `canonicalFromUI` send it back on that text, so the history `useChat` posts keeps it. Such a text stays a text part instead of collapsing to a plain string; text without round-trip data is a string as before. Gemini does not enforce text signatures (not live-verified).

`useChat` drives a native agent route with no new option. When a turn's agent state is suspended, the run's terminal frame is the authority on what it waits for: its approvals pause the chat, and its client calls run through `onToolCall` or park in `pendingToolCalls`. The hook then resumes the run in one request with `runId`, `approvalResponses` and `clientToolResults`, because `resumeStreamAgent` proceeds only with every verdict and every client result. The client calls run inside that round, so `status` is `'streaming'` while they run and `stop()` cancels it. Verdict matching and replay-safe client tools work on this path as on a chat route. New readouts: `agent` (the run's state, with `output` only once it completed) and `stopDetails`; tool calls carry `outcome`. Agent frames stay out of `onData` and `dataParts`. A chat route never sends a frame, so its requests are unchanged. The hook imports no new core export: with a core older than 2.3 it behaves as before, and `UseChatAgent` and `UseChatStopDetails` are derived from the installed core's types.

**Behaviour change:** a POST response that carries the journal's `id:` lines (a route that passes `store` and `streamId`) now moves `useChat`'s in-memory resume cursor. A `reconnect()` after a settled turn, or after a leg the hook continued with a POST, resumes after it; before, it appended the replayed turn to the history a second time. A reconnect after a dropped POST continues that turn from the last part it showed. The persisted cursor (`resume.cursor`) still moves on resume reads only, so a reload mid-turn replays the turn from its start. `setHistory` and `setMessages` drop the in-memory cursor along with the pending gates, so after a chat switch the next reconnect reads the new chat from its persisted cursor or its start, as before 2.3, never from the old chat's position. After a reload, a replay of a journal that also holds legs the restored history already has (a lost or old cursor) can still append them again.

**Behaviour change:** after an approval, the history a chat client keeps now answers the approved call. The leg that resumes a paused run executes the approved call and streams its state and result, but not the call itself. `assistantMessageFromTurn` used to put that call into the leg's turn again as a second `tool_use` without its input, which no provider accepts, and the call's result never reached the history, so the next request carried an open `tool_use`. Now `assistantMessageFromTurn` leaves out a call the turn knows only from a `tool-state` or `tool-result` frame (its UI card has no `input`), and `useChat` adds the result to `history.canonical` as a `role: 'tool'` message before the turn, on a chat route and a native route alike. The result is the one the wire carried, which is what the model saw. A call without `input` is also never handed to `onToolCall`. And when two responses name their message the same (a route that passes no `messageId` starts every response with `'deuz-msg'`), each leg now fills its own bubble; before, the continuation's text overwrote the bubble of the leg before it.

**Behaviour change:** an `onToolCall` result that lands after the chat moved on (a new message, `regenerate`, `editAndResend`, `setHistory` or `setMessages` while the call ran) is dropped. Before, `useChat` appended it after the new exchange, a history no provider accepts, and POSTed the old turn's continuation next to the new one.

The frozen `@deuz-sdk/core/react` hook is unchanged and gets none of this; fixes and features ship in `@deuz-sdk/react`.

All type changes are additive. Core `./ui`: `toDeuzAgentStreamResponse`, `agentStateFromParts`, `ToDeuzAgentStreamOptions`, `DeuzAgentFrame`, `DeuzAgentResultFrame`, `DeuzAgentState`, `DeuzAgentStatus`, `DeuzAgentClientCall`, `DeuzAgentUnknownEffect`, and the optional fields `stopDetails` (the `finish` and `step-finish` members of `DeuzUIPart`), `outcome` (its `tool-state` and `tool-result` members), `providerMetadata` (its `text-delta` member) and `ReadDeuzStreamOptions.onEventId`. Core `./chat`: the optional `AssistantTurnState.agent`, `AssistantTurnState.stopDetails`, `UIToolCall.outcome` and the `providerMetadata` of the `text` member of `UIMessagePart`. React: `UseChatResult.agent` and `UseChatResult.stopDetails`, and the types `UseChatAgent` and `UseChatStopDetails`. No union gains a member, and no persisted format changes.
