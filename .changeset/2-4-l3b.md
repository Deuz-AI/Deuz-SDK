`runAgent`, `streamAgent`, `resumeAgent`, `resumeStreamAgent` and `reconcileAgentRun` take a V3 path: pass `checkpointVersion: 3` with a session on an `AgentRunStoreV3` (`createInMemoryAgentRunStoreV3`, `createSqliteAgentRunStoreV3`, `createPostgresAgentRunStoreV3`). The same executor runs both paths. A V3 run saves every record as version 3, terminal and bookkeeping saves included, and `streamAgent` returns an `AgentStreamV3` whose `eventsV3` carries every 2.3 event plus the V3 ones: `context` (a step's manifest), `working-memory` (a new revision) and `memory-intent` (a versioned-memory write moving on). The stream is still an `AgentStream`, so `toDeuzAgentStreamResponse` serializes it as before and none of the compiled context reaches the wire. A V3 run refuses a missing session or a 2.3 store with a `TypeError`, and a Redis store with `UnsupportedStoreError` (code `unsupported_store`), before anything is read or written. Without `checkpointVersion: 3` nothing changes. A 2.3 run that passes `context`, `workingMemory` or `versionedMemory`, or a V3 store, is now refused with a `TypeError` instead of having those options silently ignored.

`context` puts the context compiler into the native loop. It takes a `ContextCompiler` or the options of `createContextCompiler`, and a resumed run restores the compiler's state from the run record. Each model step runs in the spec order: compaction, then your `prepareStep`, then the step's real model and active tools, then a source refresh when one is due, then the compile with the final budget check (the tool schemas, the output schema of a final answer call and the provider framing are counted). The package is then written as a content-addressed blob (an unchanged package is written once) and its manifest is saved with the run, all before the model call. Retrieval enters the history append-only, right after the messages it was compiled for and only once the call succeeded, and it never reaches the chat transcript. The working memory ends each request as an ephemeral tail and is never written to history, except on a model that binds preserved thinking to the transcript prefix (Claude 5.x): there each step's copy joins the history once the call succeeded, right after that step's retrieval, so the bytes before every replayed thinking block stay the same. Each copy says it replaces the earlier ones, the next request ends with the current one, and the manifest records `placement.tailKept`. The system message and the tool schemas never change, so a refresh keeps the prompt-cache prefix, and the manifest records whether it changed (it does at a compaction boundary). A native final answer call carries its context the same way, so a structured-output run without tools is compiled too. `deuz.context.compile` now nests under the step's span. A host estimator given as `context.estimator` is calibrated with each call's real prompt size.

On a provider overflow, the loop compacts again as before (it does not re-run `prepareStep`), and the compiler places the step's context again for just under the size of the request that overflowed: optional context shrinks, the step's package is replaced (refresh `'overflow-retry'`), and mandatory content that cannot fit fails the run with `ContextBudgetExceededError` (code `context_budget_exceeded`). A step whose package placed nothing, with nothing compacted, keeps the provider's overflow error as in 2.3. A step that is reopened after a restart (same messages, answer never saved) uses its stored package again without asking the sources. A package that a `forget` redacted is compiled again (refresh `'redacted'`, `redacted: true` in its manifest), and when a run resumes, the retrieval blocks of redacted packages are removed from its history and checkpoints before the next request.

Memory placed by the compiler and the legacy automatic recall would inject the same memories twice. A V3 run whose compiler has a memory source and whose `memory.recall` is on is refused at configuration time. Set `memory.recall: false` to keep only the legacy extraction. Without a memory source, the legacy recall works as in 2.3.

`workingMemory: { snapshot?, create?, tools? }` keeps the working memory, with the task list and the active task, in the V3 record. A resumed run keeps the stored snapshot, so the active task survives a restart. Working memory without a compiler still gets its tail placed. With `tools: true` the model gets `working_memory_read`, `working_memory_add` and `working_memory_update`; a model's patch becomes durable in the same save as its tool receipt, and a call replayed after a crash is applied once. A host tool with one of these names is refused, and so is a snapshot or a `create` for another scope than the session's.

`versionedMemory: { session, tools?, extract? }` connects a versioned memory session. Its writes follow durable intent, prepared plan, atomic memory commit with its receipt, then native acknowledgment, and they are recorded in `memoryIntents`. With `tools: true` the model gets the session's memory tools. Each write's intent moves with its tool receipt (`intended`, `committed`, `acknowledged`) under the session's operation id. `extract` (off by default) extracts the completed run's turns into the session: its intent is saved in the terminal commit, the run saves its claim on it (`planned`, the status only) before the session runs, the session prepares the plan and commits it with its receipt in one call, and the acknowledgment copies the receipt into the intent (its mutation count as `planned`, and `requestDigest`, the digest of the request rather than of the plan). A lost acknowledgment is settled from the receipt (a resume replays the tool call; `reconcileAgentRun` with `versionedMemory: { session }` replays the extraction and returns the settled operation ids in `memoryIntents`), and a memory change is never applied twice, even when a model call repeats after a crash. In a V3 run, a legacy extraction that wrote only part of its plan is recorded as `'partial'` and reported with a `memory-extraction-partial` warning; `reconcileAgentRun` reports it as `'failed'` in its 2.3 answer shape.

Behaviour change: the built-in memory of native runs (`memory`) reports its 2.4 warnings on the run's stream (`embedding-mismatch` from the recall, `unaccounted-usage` for a memory LLM or embedder that reports no usage). It also charges the memory LLM and embedder calls to the run's execution context, unless you set `seams.execution` yourself, so they count against the run's budget and execution policy. The legacy loops (`generateText`, `streamChat`) report the same warnings in `warnings` and charge `execution` when the call has one.
