A stable transcript prefix for Claude 5.x's preserved thinking. Claude Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5 bind every thinking block to the conversation before it: the top-level `system`, the `tools` array and every earlier message have to reach the API byte-identical on every later request, or the replayed block is invalid (a 400 on accounts opened from 2026-08-31). The agentic loops now keep that prefix stable for these models, and for an unknown `claude-*-5…` id on the family fallback, so the `block_binding: drop_block` default that 2.3 sends with replayed thinking is the safety net rather than the normal path. Every other model keeps its 2.2 requests, apart from the two wire changes noted below. Request shapes follow `@anthropic-ai/sdk` 0.133.0; not live-verified. New guide: Agents → Preserved thinking.

The top-level system slot is the leading run of `system` messages. A system message after the first non-system message is a mid-conversation system message: Claude 5.x receives it in place as a `role: 'system'` message, OpenAI Responses as a `system` input item in place, Chat Completions in place as before, and Gemini and the older Claude models keep the 2.2 fold into the top-level instruction. **Behaviour change:** on OpenAI Responses (every model) a system message from the middle of the history no longer moves into `instructions`; it stays where it is, as a `system` input item. A system message without text is sent by no wire.

Memory recall on Claude 5.x is one appended system message instead of a block spliced into the system prompt at every call. It is recalled once per user turn, appended right after the question it was recalled for (after the `onInput` guardrails, before the first model call), and it is part of the conversation: it rides in the run's history (so checkpoints keep it), in `response.messages` and in the chat record, carrying `providerMetadata: { deuz: { memoryRecall: true } }`, so the next turn sends it back where the model saw it. A history whose last user message is already followed by its recall message recalls nothing: a durable resume leg, an approval continuation built from `response.messages`, a replayed transcript. The extraction pass ignores system messages, so recalled memories are never written back. **Behaviour change** (Claude 5.x only): `response.messages` and the chat record now hold that system message; other models keep the recall-free transcript. `uiFromMessages` does not render system messages, and `useChat` does not post them, so a route that wants the prefix to hold across turns loads its history from its chat store.

Handoffs to a Claude 5.x target append the target's `instructions` as a system message after the transfer's tool result instead of rewriting the run's leading system turn; a target without `instructions` appends nothing, so the run's own system prompt stays in force. The message lives in the run's history and checkpoints, not in `response.messages` or the chat record, as the rewritten turn did. When the transfer's step breaks (an approval, a client tool, a suspended sub-agent), the resume leg answers the step's pending calls ahead of that message, right after the transfer's tool result. **Behaviour change** for those targets: the run's system prompt is no longer replaced or removed. Other targets keep the 2.2 rewrite.

`promptInjectionGuard()` adds its notice once: a history whose leading system run already carries the policy text (a chat record saved by an earlier guarded call) is left as it is, where it used to gain one more copy per turn. `instructions` folds once over the whole leading system run, not only when it is the first message, so a guard notice saved ahead of it no longer produces a second copy either. Both apply to every model.

On Claude 5.x the `tools` array stays the same on every request of a run leg: the root agent's tools (MCP tools merged in) filtered by the call's static `activeTools`. A step that offers another set — `prepareStep.activeTools`, a handoff target's tools, an MCP `tools/list_changed` — appends one system message carrying the change (`providerMetadata: { deuz: { toolChanges: { remove, add } } }`), which the Anthropic wire sends as `tool_removal` / `tool_addition` blocks under the beta `mid-conversation-tool-changes-2026-07-01`, with `inline-tools-2026-09-15` added when a definition rides inline. Like the recall message it is conversation content (`response.messages`, the chat record), and a replayed removal that names a tool the request no longer declares is left out. The step's tool calls resolve against the set it offered, so a call to a withdrawn tool is answered like an unknown tool and never runs. Other models keep a per-step `tools` array.

Compaction for Claude 5.x is simple: one summary replaces the whole conversation, so no thinking from before it is replayed behind a rewritten prefix. The leading system messages, the later system messages that carry run state (handoff instructions, tool-set changes, your own) and the pending user turn with its recall message stay; an older recall block is summarized with its turns. The prune layers never run on their own for these models: with `'auto'` or any policy that lists `summarize` they fold into the summary, and a prune-only policy compacts nothing and reports each skipped layer. Overflow recovery runs the same simple pass. `compactMessages` takes the model the history goes to next (`CompactMessagesDeps.model`) and compacts simple for these models. Anthropic's server-side compaction is not used: its signed `compaction` blocks would need a new canonical part kind, which 2.x does not add.

Known limit: handoff instructions stay out of the transcript, so the first request of the call after a handoff drops the thinking of the turns that followed the transfer (the `drop_block` safety net, no error).

Additive types, no new export: `CompactMessagesDeps.model`. No union gains a member and no persisted format changes: the recall and tool-set change messages are ordinary `system` messages with message-level `providerMetadata`.
