**A native resume answers a call from its receipt when the receipt records the call's outcome.** A native run saves a call's receipt before the step checkpoint that answers the call, so a run can stop in between: its process dies during the next model call, a store write fails, or a sub-agent called in the same step suspends on its own approval. The next resume found the call unanswered and ran the approval gate again. A call that had waited for an approval (`needsApproval`, or the execution policy's `requireApproval`) was then answered `Tool call denied. Reason: No approval response.` unless the resume passed its verdict again, so the model was told the call had been denied although its effect had landed and its result was recorded.

This is a behaviour change. Such a call is now answered from its receipt exactly like a call that needs no approval: the policy and the `onToolCall` guardrails still apply, the receipt answers the call through the normal tool path (`onToolResult` included), and the tool never runs again. A receipt records an outcome in stage `executed`, `completed`, `failed`, `validation-failed` or `projection-failed`, including one recorded with `reconciledToolResults`. The resume needs no verdict for such a call. A verdict passed for it anyway, an approval or a denial, decides nothing: the resume ignores it and streams a `warning` part (`type: 'other'`, `setting: 'approvalResponses'`) that names the call. A call without a recorded outcome is gated as before: one that never started, one in `executing` that `retryToolCallIds` runs again, and a sub-agent call in `suspended`; without its verdict it is answered as denied. This holds for `resumeAgent` and `resumeStreamAgent`, for a run's own tools, a handoff target's tools and MCP tools, which share the run's receipts. A client tool keeps its rule: a client call whose result the resume does not supply is still answered `Tool call denied. Reason: No result provided for this client tool.`

**A leased native run can be drained.** A `'drain'` signalled to the key of a native run that holds a `lease` (`leases.signal(agentRunLeaseKey({ scope, runId }), 'drain')`) used to be ignored. The executor now picks it up at its next renewal and stops the run at its next model-step boundary, for example to move the run to another process during a deploy. Nothing in progress is interrupted: the step's model call and tool calls finish, a model call that fails over goes to the next model first, and no further model call starts. The result is `stopped` with the new stop reason `'drained'`; on a stream, the `finish` part of a run that stopped after a step also names it (`providerMetadata.deuz.stoppedBy: 'drained'`). The run has not ended. No outcome is committed: it stays as its last save left it, a run stopped after a step exactly as after any other step (a run with `chat` still saves its chat projection, as after any leg), so a resume on any executor goes on from there and nothing that ran runs again. A new run stops before its first model call, once it is saved; a run with `output` stops before its final answer call, or before a new one after an invalid answer or a rejected verdict. A resume that the drain reaches before it takes the run up writes nothing; one that already took the run up goes on to its first step boundary, so the verdicts and client results it was given are applied and saved first. Any other stop at the same point comes first (`maxSteps`, a budget), and a cancel or an abort of the run's `signal` outranks a drain. As for a swarm, the signal concerns the executor that holds the run: it is dropped when the run changes hands or the lease is released. Unlike a drained swarm, which settles as `'suspended'`, a drained native run keeps its phase, so `findStaleAgentRuns` finds it as it finds a run whose executor died.
