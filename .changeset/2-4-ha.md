**Embedding generations work the same way on every versioned memory store.** The store prepares one generation at a time. `embeddings.begin` with another model or size retires the pending generation and deletes its vectors in the same transaction, so an abandoned `reembed` leaves no vectors behind. A job that is still filling the retired generation ends quietly with `activated: false`. A retired or unknown generation stays retired: `pending` lists nothing for it, `put` stores nothing and returns `0`, and `activate` returns `false`. A generation that an activation replaced never becomes active again. Before this, the SQLite and PostgreSQL stores kept every pending generation, threw `InvalidRequestError` from `put` and `activate`, and could make a retired generation active again. The in-memory store already behaved as described.

**`ConditionalChatStore.pruneTombstones` on PostgreSQL accepts a fractional cutoff.** Before, a cutoff such as `1000.5` failed inside the driver. The store now compares the cutoff as its whole-millisecond ceiling, so it removes the same tombstones as the in-memory and SQLite stores.
