Native runs (`runAgent`, `streamAgent`, `resumeAgent`) put MCP tools behind the same effect receipts as local tools. An MCP call records `executing` before the server is called, so a resume after an interrupted call stops with `tool-reconciliation-required` instead of calling the server again and repeating the paid model turn. Each call emits a native `tool-output` event, and tools that arrive through a `tools/list_changed` hot refresh are covered too. The servers' tool catalog is pinned in the resume binding as `AgentRunEnvelope.binding.mcp` (the `fingerprintTools` JSON). A resume whose catalog gained, lost or changed a tool fails with `MCP tool catalog changed across resume (...)` and leaves the stored run untouched. A hot refresh mid-run records the new catalog before the model is offered it and reports the change as a `warning` part with `setting: 'mcp'`. A run checkpointed before 2.3 records the catalog it is resumed with. An `mcp` entry may declare `replay: 'idempotent'` for the whole server, or per tool by the server's own tool name, so an interrupted call of that tool runs again on resume (`AgentMcpEntry`, `AgentMcpReplay`; `AgentRunOptions.mcp` widens to accept them). The declaration never enters the connection pool key. An MCP tool's raw JSON Schema `outputSchema` stays metadata, because the MCP client validates structured results, instead of failing native preparation. The servers are connected after a terminal run has returned and before anything is persisted: a terminal run never reconnects, and an unreachable server fails a fresh run before its first checkpoint or model call. `ResolvedMcpRuntime` gains an optional `origins` map (entry index and server tool name per merged tool).

Native tool receipts gain an additive `'failed'` stage (the `AgentToolReceipt['stage']` union widens). A tool whose `execute` threw has already answered the model with that error, so a resume replays the recorded error instead of stopping for reconciliation; `'executing'` still means an unknown outcome. Handoff transfers now work in native runs: native tool preparation dropped the transfer marker, so the transfer tool's throwing body ran instead of handing the run over. A target agent's own tools carry the same receipts.

A turn the provider refused (`content_filter`, Anthropic `stop_reason: 'refusal'`) or cut off (`length`, `max_tokens`) no longer dispatches its tool calls in `generateText`, `streamChat` or native runs, because their arguments can be truncated JSON. A tool call whose arguments are not a JSON object is never executed and self-heals into an `is_error` result. An empty assistant turn is never stored or sent back, and `doneWhen` and `verifyStep` do not re-drive such a turn. A provider's stop explanation is surfaced as `StopDetails` on `GenerateTextResult.stopDetails`, `StepFinishPart.providerMetadata`, the streaming loop's `finish` part and `AgentResult.stopDetails`. A native run that ends on a refusal stops with the new reason `'refusal'` instead of the raw `'content_filter'`.

The finalization request of a native run with tools and `output` ends with a user turn instead of the loop's last assistant answer, a prefill that Claude 5.x models reject with HTTP 400 (inferred from Anthropic's documented rules; not live-verified). That turn is persisted once, so the transcript stays append-only. Finalization asks for the loop's own tools with `tool_choice: 'none'`: a text re-drive after a rejected verdict sends them today, and a structured request will once the provider adapters send tools alongside the output format. The stored answer is the full assistant message, reasoning included.

Native runs re-check cancellation and the execution deadline after async output validation, guardrails and the verifier. An abort during verification stops the run with reason `'aborted'`, also when the verifier throws because of it, instead of completing or reporting `verification-inconclusive`. A deadline that elapsed during verification fails the run with the same `ExecutionPolicyError` that model and tool dispatch raise. A completed result that was already committed is never rewritten.

Envelopes written by 2.2 still resume. An envelope that records an MCP catalog or a `'failed'` receipt needs 2.3 or later to resume.
