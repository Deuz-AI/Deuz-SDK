`@deuz-sdk/core/testing` gains versioned eval suites. `runEvalSuite(tasks, options)` runs `EvalTaskManifest`s: each task has a stable `id` and a `version`, a start snapshot (`messages`, workspace `files`, JSON `store` state) that every attempt gets its own copy of, acceptance criteria (graded as `runGradedEval` grades a case) and an optional `grade` for partial credit, the tools it may call and the file `scope` it may change, the model, protocol and effort it is meant for, a budget, a timeout, repeats, required artifacts, the tools whose approval is part of the task, and, for a fault scenario, the fault boundary and the recovery its documentation promises. A task's `run` gets an `EvalTaskContext` (an in-memory observer to pass as `deps.observer`, an abort signal for the timeout, and `effect`, `approve`, `rescue`, `interrupt` and `artifact` recorders) and returns an `EvalTaskOutcome`, which a native `AgentResult` already is. Every attempt reports success, score, false completion (the run claimed `completed` and failed acceptance), cost and tokens from the run's accounting across every leg, duration on an injectable clock, human rescues counted apart from required approvals, repeated effects, the tools it called, and how it came back from an interruption (`EvalRecovery`: `not-needed`, `recovered`, `rescued`, `contained` or `failed`). Beyond its acceptance, an attempt fails when it executed an effect twice, called a tool outside the allowed set, changed a file outside its scope, went over budget, missed a declared artifact, or for a fault scenario never hit its fault or recovered another way than documented. Metrics add up per task and per tier: `'offline'` and `'real-model'` tasks are separate experiments and never aggregated together, and `skip` lists a task (a missing key, say) without running it. A thrown or timed-out run is a failed attempt, never a crash; a malformed suite throws a `TypeError` before any task runs. The JSON report (`EvalSuiteReport`, `format: 'deuz-eval-suite'`, version 1) is returned and written only on request, to a file path (through `node:fs`, loaded only then, so the subpath stays edge-safe) or to a callback. The 2.3 baseline lives in the repository: 16 offline tasks and 19 fault-injection scenarios (before dispatch, after approval, between effect and receipt, between receipt and checkpoint, mid model stream, verifier abort and deadline, child initialization, swarm cancel commit, lease loss and renew failure, admission store failure, settle failure, spawn commit failure, MCP hot refresh, and a refused or cut-off turn that carried a tool call) run on every `npm test`, and five real-model tasks are defined but not run (not live-verified). It is a baseline, not a ranking. See the new Evals page.
