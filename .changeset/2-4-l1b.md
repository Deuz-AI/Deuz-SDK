Versioned memory gets its SQLite and PostgreSQL stores. `createSqliteVersionedMemoryStore` (`@deuz-sdk/core/memory/versioned/sqlite`) and `createPostgresVersionedMemoryStore` (`@deuz-sdk/core/memory/versioned/postgres`) keep records, their immutable revisions, operation receipts, embedding generations and vectors in new tables with their own `deuz_vmem_schema` version table, beside the existing memory tables, which they never touch. Each operation is committed in one transaction (record, revision, search index, vector and receipt together, or nothing), a repeated operation id replays its receipt, and search fuses full-text and vector ranking: FTS5 with a LIKE fallback on SQLite, a `simple` tsvector with a GIN index on PostgreSQL, and cosine over the active embedding generation (computed in the database when pgvector is installed, over the freshest `candidateLimit` rows, default 1000, otherwise). The PostgreSQL store needs a pool (`pg.Pool` or compatible); a client that only offers `query()` is refused. Both stores take a `clock`, a `logger` (`pruneOperations` warns through it) and an `observer` (`pruneHistory` and `pruneOperations` report `deuz.memory.op` spans).

Behaviour change in the existing memory stores (in-memory, Markdown, SQLite, PostgreSQL and Redis): a vector query no longer fills its results with records that have no vector at score 0, and a record whose stored vector has another length or another `embeddingModelId` than the query's no longer enters the vector ranking. Both are still found by their text. `recall` names the embedder's model on the query and reports such records once per run as an `embedding-mismatch` warning (through the new `onWarning` option, or one logger line per seams and mismatch). A store that implements its own `search` can do the same with the new `MemoryQuery.embeddingModelId` and `MemoryQuery.onEmbeddingMismatch`. The PostgreSQL store no longer tops up a short pgvector result with records that have no vector.

Behaviour change: `memory_update` now drops the record's stored vector, because it was computed from the old text, and every built-in store's `update` drops it when the text changes without a new embedding. The record is found by text until it is embedded again; no embedding call is added.

`MemorySeams.llm` also accepts an accounted memory LLM (`defineAccountedMemoryLLM`, now exported from `@deuz-sdk/core/memory` together with `isAccounted`), and `MemorySeams.embedder` an accounted memory embedder. With the new `MemorySeams.execution`, every memory LLM and embedder call is reserved on that execution context's ledger first: an accounted callback settles the usage it reports, an unmarked one is counted as unaccounted (never as free) with one `unaccounted-usage` warning. Without `execution` nothing is charged, as before.
