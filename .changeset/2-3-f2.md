'@deuz-sdk/core': minor
---

Goals, wakeups and events get a data contract: the new `@deuz-sdk/core/goal` subpath (edge-safe, pure; nothing in it runs a model, a timer or a service). A `GoalRecord` (version 1) holds a goal's identity, scope, parent goal and current native run, an objective, acceptance criteria, evidence references, the latest verdict per criterion, a budget with what was spent, a deadline and a lifecycle: `active`, `waiting` with an explicit reason (`user`, `event`, `dependency`, `wakeup`, or `budget` once a charge reached a limit), `completed`, `failed` or `cancelled`. `createGoal` makes one and `transitionGoal(record, command, { now, expectedRevision? })` is the only way it changes, one revision at a time, never touching the record it is given: `wait`, `resume`, `event`, `evidence`, `evaluate`, `complete`, `fail`, `cancel`, `charge`, `revise`, `link-run` and `tick`. It reports what it did as `applied`, `ignored` or `rejected`, with a reason; a malformed record or command, an event for another goal and an `expectedRevision` the record is not at throw `GoalError` (`invalid_goal`, `invalid_command`, `invalid_event`, `scope_mismatch`, `revision_conflict`). A goal is done only on evidence: `assessGoal` gives each criterion and the goal `passed`, `failed` or `inconclusive`, a `passed` verdict counts only when something other than the working model reached it on evidence from outside the model, and `complete` is rejected until every required criterion passed that way. A passed deadline fails the goal at the next transition, and a spent budget holds it until a revision raises the budget, keeping the wait it interrupted (events that answer that wait still apply) and putting it back then.

A `GoalEvent` (version 1) is the wakeup and event envelope: identity, source, scope, goal and run, a dedupe `key`, the time it happened with `notBefore` and `expiresAt`, a payload reference and a `correlationId` naming the wait it answers. Its key shares one space with the schedule's occurrence keys (`<id>@<at>`) and `handleSignal`'s keys (a delivery ID or `sha256:<hex>` of the body), so one durable claim dedupes them all: `goalEventFromOccurrence`, `goalEventFromSignal` and `goalWakeupEvent` (keyed `goal:<goalId>@<at>`, see `goalWakeupKey`) build them, `createGoalEvent` takes your own. A goal applies an event that answers its wait and remembers its key, and remembers a charge's key in a window of its own, so a run's charge and its completion event may both be keyed by the run ID; it drops a duplicate, an expired or early event, one answering an earlier wait or older than the wait, and one it does not wait for, each with its reason. `parseGoal`, `serializeGoal`, `parseGoalEvent` and `serializeGoalEvent` read every version up to their own, keep fields a later 2.x release adds, and refuse a newer version with `unsupported_version`. `GoalStore` is the host's persistence boundary (copies, a save only at the next revision, an optional `list`), and `createInMemoryGoalStore` is its reference implementation. A running supervisor, a durable inbox and timezone-aware wakeups remain 2.4 work.

Native runs can be listed. `AgentRunStore` gains an optional `list({ phases?, updatedBefore?, scope?, limit?, cursor? })` that resolves a page of run summaries (`runId`, `scope`, `phase`, `revision`, `updatedAt`, and the stored result's `status`, so a suspended run is told apart from one in progress), newest save first, with a `cursor` while more follow. `createInMemoryAgentRunStore` (which now takes an optional `clock`) and the SQLite and Postgres `agentRuns` implement it; the SQL stores page by the `deuz_agent_runs_updated_at` index added on first use, with no schema version change. `findStaleAgentRuns(store, { staleMs?, scope?, includeSuspended?, limit?, clock? })` from `@deuz-sdk/core/ops` finds the runs still running or finalizing whose last save is older than `staleMs`, for a worker to resume.

`runAgent`, `streamAgent`, `resumeAgent` and `resumeStreamAgent` take a `lease` option, `{ provider, owner?, ttlMs? }` as `createSwarm` does, so two processes never drive one native run. The executor holds the run's key (`agentRunLeaseKey({ scope, runId })`) from before it reads the run until it returns, renewing it every `ttlMs / 3`. While another executor holds it the run fails with code `'lease_held'` before anything is read or written; an executor that loses it aborts and writes nothing more, failing with `'lease_lost'`. A `'cancel'` signalled to the key stops the run with the new stop reason `'cancelled'`; with a provider that acknowledges cancels, it stays queued until the stopped run is saved, so an executor that dies in between cannot lose it, and the next executor to claim the run applies a cancel still queued before any model call. Without the option nothing changes.

Widened public types: `AgentRunStore` gains the optional `list`, `AgentRunOptions` the optional `lease`, and the SQLite and Postgres ops stores' `agentRuns` declare `list`. New types: `AgentRunPhase`, `AgentRunListQuery`, `AgentRunSummary`, `AgentRunListPage`, `AgentRunLeaseOptions`, `FindStaleAgentRunsOptions`, and the goal module's types.
