A model in the registry, or a protocol in a module, is not a promise that it works against the provider's live API. This page says, for every model row and every protocol 2.3 added, which of three levels of verification it has reached. The levels are kept apart on purpose: a documented rule that is tested offline is still not live-verified.

| Level | What it means |
| --- | --- |
| **Documented** | The behaviour follows the provider's official documentation as of the date given, or the type definitions of the provider's official npm package at the version given. It records what the provider states, not that the provider accepts what Deuz sends. |
| **Fixture-tested** | Offline tests in `packages/core/test`, run by every `npm test` with no API key and no network beyond `127.0.0.1`. They pin what Deuz sends and how it reads a scripted answer. Where the table below says so, the other side is the official MCP or A2A SDK, installed as a devDependency; elsewhere it is a stand-in written from the provider's documentation and SDK types. |
| **Live-verified** | Checked against the provider's real API with a real key. |

<Callout type="warn" title="Nothing in 2.3 is live-verified">
No model row and no protocol 2.3 added was run against a live provider, so the live column below is "no" everywhere, and `resolveModelProfile(model).liveVerified` is always `false`. The repository's opt-in live smoke tests (`packages/core/test/live`, `npm run test:live -w @deuz-sdk/core`, keys in `.env.smoke`) date from before 2.3: they call DeepSeek `deepseek-v4-flash`, Gemini `gemini-3.6-flash` and xAI `grok-4.5`. 2.3 added ten [real-model eval tasks](/docs/modules/evals#real-model-tasks) to the same command, and defines an eleventh, the batch twin, that no runner submits; they are defined but have never run. None of these ran for 2.3.
</Callout>

The test files below are named without their `.test.ts` suffix and live in `packages/core/test`.

Deuz reads a stop explanation from Anthropic (`stop_details`, with a refusal's category) and from OpenAI (the refusal text, without a category). It reads none from Gemini: a Gemini candidate's `finishMessage` is not read, so a Gemini stop has no `stopDetails`.

- **Streams, Gemini.** The streaming adapter behind `generateText`, `streamChat`, the object calls and native runs maps every `FinishReason` value of `@google/genai` 2.28, each with a fixture (2.3). The filters `SAFETY`, `RECITATION`, `BLOCKLIST`, `PROHIBITED_CONTENT`, `SPII`, `IMAGE_SAFETY`, `IMAGE_PROHIBITED_CONTENT` and `IMAGE_RECITATION`, and a blocked prompt, end a turn with `content_filter`; before 2.3, `SPII` and the last two ended it with `'stop'`. `MAX_TOKENS` and `CONTINUATION` end it with `length` (Deuz sends no continuation token; `CONTINUATION` ended it with `'stop'` before 2.3), `STOP` and `FINISH_REASON_UNSPECIFIED` with `stop`, and so do the stops that leave no usable answer (`LANGUAGE`, `OTHER`, `MALFORMED_FUNCTION_CALL`, `UNEXPECTED_TOOL_CALL`, `TOO_MANY_TOOL_CALLS`, `NO_IMAGE`, `IMAGE_OTHER`), as before 2.3. A value 2.28 does not list ends it with `stop`. The `finish` part keeps Gemini's own value as `providerMetadata.google.finishReason` (2.3), which tells those stops from `STOP`. A turn that streamed a call ends with `tool_calls` unless a filter or a limit stopped it; before 2.3 the call won over every reason.
- **Streams, OpenAI.** Chat Completions' `finish_reason` maps one to one, with the deprecated `function_call` as `tool_calls`. A Responses turn ends with `length` when `incomplete_details.reason` is `max_output_tokens` and with `content_filter` when it is `content_filter`; before 2.3 the latter ended with `'stop'`, or `'tool_calls'` when the turn streamed a call. `max_messages` and `steered`, which `openai` 7.32 does not document beyond the name, end it as a complete response does. A refusal on either wire ends the turn with `content_filter` unless the provider reported `length` or `content_filter` itself, also when the stream closed before its last event (Chat Completions without a `finish_reason`, Responses without `response.completed` or `response.incomplete`). Before 2.3 the refusal was dropped, so a refused turn ended with `'stop'` (or `'tool_calls'`) like an empty answer. The refusal never becomes answer text.
- **Batch results.** The batch parsers share the streaming adapters' mapping, so a batch result ends as the same reply does when streamed: the same finish reason, for an OpenAI refusal the same `stopDetails` and `providerMetadata.openai.refusal`, and for Gemini the same `providerMetadata.google.finishReason`.
- **Tool calls.** Whatever the provider, a turn that ends with `content_filter` or `length` dispatches none of its tool calls (2.3; `finish-gate` replays the Anthropic wire, `finish-gate-providers` the Gemini, Responses and Chat Completions wires). That covers a Gemini filter or limit after a call, an OpenAI turn its content filter stopped, and an OpenAI refusal. A turn that ends with any other reason is not held back: a Gemini stop without a usable answer after a call ends with `tool_calls`, and its call runs, as before 2.3.

## 2.4

2.4 adds no model row and no provider protocol, and nothing in it was run against a live provider: every model call its features make (memory LLM and embedder callbacks, native runs under the goal supervisor, verifiers, skill proposals) is tested against scripted models. What 2.4 adds is verified against the backends it runs on.

| Surface | In every check run (offline) | Against a real backend |
| --- | --- | --- |
| SQLite stores: versioned memory, goal runtime, V3 runs, conditional chats with their transcript index, durable streams, process operations | Real `node:sqlite` databases | The same |
| PostgreSQL stores: versioned memory, goal runtime, V3 runs, conditional chats with their transcript index, durable streams | PGlite | Postgres 16 in the CI integration job (`DEUZ_TEST_POSTGRES_URL`). The pgvector path of the versioned memory store only against an emulated `vector` type in PGlite |
| Redis durable stream store | ioredis-mock, which runs the same Lua scripts | Redis 7 in the CI integration job (`DEUZ_TEST_REDIS_URL`) |
| Docker sandbox and process runner (preview) | A scripted Docker CLI | A Docker Engine with Linux containers (`DEUZ_TEST_DOCKER=1`): GitHub's ubuntu runner in the CI Docker job, and Docker Desktop on Windows 11 locally |
| Webhook handler | GitHub, Slack and HMAC signatures computed in the tests with `node:crypto` | Not against deliveries from GitHub or Slack |
| Time zone schedules | The host's `Intl` time zone data, across DST gaps and overlaps | Not applicable |

Golden fixtures recorded with 2.3.0 (179 scenarios across the provider factories) check in every run that, with the 2.4 features off, the provider requests (method, URL, headers and body bytes) are the ones 2.3.0 sent. See [What is new in 2.4](/docs/reference/whats-new-2-4#known-limits) for the release's known limits.
