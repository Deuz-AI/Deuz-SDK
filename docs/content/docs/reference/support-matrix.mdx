A model in the registry, or a protocol in a module, is not a promise that it works against the provider's live API. This page says, for every model row and every protocol 2.3 added, which of three levels of verification it has reached. The levels are kept apart on purpose: a documented rule that is tested offline is still not live-verified.

| Level | What it means |
| --- | --- |
| **Documented** | The behaviour follows the provider's official documentation as of the date given, or the type definitions of the provider's official npm package at the version given. It records what the provider states, not that the provider accepts what Deuz sends. |
| **Fixture-tested** | Offline tests in `packages/core/test`, run by every `npm test` with no API key and no network beyond `127.0.0.1`. They pin what Deuz sends and how it reads a scripted answer. Where the table below says so, the other side is the official MCP or A2A SDK, installed as a devDependency; elsewhere it is a stand-in written from the provider's documentation and SDK types. |
| **Live-verified** | Checked against the provider's real API with a real key. |

<Callout type="warn" title="Nothing in 2.3 is live-verified">
No model row and no protocol 2.3 added was run against a live provider, so the live column below is "no" everywhere, and `resolveModelProfile(model).liveVerified` is always `false`. The repository's opt-in live smoke tests (`packages/core/test/live`, `npm run test:live -w @deuz-sdk/core`, keys in `.env.smoke`) date from before 2.3: they call DeepSeek `deepseek-v4-flash`, Gemini `gemini-3.6-flash` and xAI `grok-4.5`. 2.3 added five [real-model eval tasks](/docs/modules/evals#real-model-tasks) to the same command; they are defined but have never run. None of these ran for 2.3.
</Callout>

The test files below are named without their `.test.ts` suffix and live in `packages/core/test`.

| Stop details and refusals, other providers | `finishReason: 'content_filter'` without `stopDetails` | `openai` 7.32's and `@google/genai` 2.28's types | Batch results: `batch-parse` (Gemini safety stops and a blocked prompt, Chat Completions' and Responses' `content_filter`, a Responses refusal). Streams: a Gemini blocked prompt only (`google-native`) | No |

On the "other providers" row: no provider but Anthropic sends a stop explanation that Deuz reads, so `stopDetails` is Anthropic-only.

- **Streams.** The streaming adapters behind `generateText`, `streamChat` and native runs map these as before 2.3. Gemini's `SAFETY`, `RECITATION`, `BLOCKLIST`, `PROHIBITED_CONTENT` and `IMAGE_SAFETY` finish reasons and a blocked prompt end a turn with `content_filter`, as does Chat Completions' `finish_reason: 'content_filter'`; only the blocked prompt has a fixture. The other filtering values `@google/genai` 2.28 lists (`SPII`, `IMAGE_PROHIBITED_CONTENT`, `IMAGE_RECITATION`) end it with `'stop'`. OpenAI's own refusal output is not read: a `refusal` delta (`delta.refusal` on Chat Completions, `response.refusal.delta` on Responses) is dropped, and a Responses turn cut off by its content filter ends with `'stop'`, or `'tool_calls'` when it streamed a call.
- **Batch results.** The 2.3 batch parsers map the same Gemini and Chat Completions values, also map a Responses `incomplete_details.reason` of `content_filter` to `content_filter`, and keep OpenAI's refusal text as `providerMetadata.openai.refusal`.
- **Tool calls.** Whatever the provider, a turn that ends with `content_filter` or `length` dispatches none of its tool calls (2.3; `finish-gate` replays the Anthropic wire). A turn that ends with any other reason, such as the Responses cases above, is not held back.
