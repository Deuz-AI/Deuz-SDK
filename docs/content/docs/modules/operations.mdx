A durable swarm or native agent run can outlive the process that started it.
The operations surface (2.2) decides which process drives a run right now,
lets another process take over when that one dies, and lets any process drain
or cancel a run.

Two mechanisms keep this safe:

- A **lease** is liveness. The executor holding a run's lease drives it and
  renews the lease on a heartbeat. An executor that loses its lease stops before
  its next write.
- A **revision** is the fence. Every swarm commit and every native agent save
  names the revision it expects. A store rejects a stale one, so a paused
  "zombie" executor that wakes up after a takeover cannot overwrite the new
  executor's progress, even if its heartbeat has not noticed yet.

## Leases

A `LeaseProvider` hands out one lease per key. `acquire` returns `undefined`
while another owner holds the key. Every change of hands increases the lease's
`token`. `renew` extends the lease and delivers queued signals once each; a
lapsed lease that nobody else took can still be renewed. `release` ignores a
stale token. `signal(key, 'cancel' | 'drain')` queues a request for whoever
holds the key and reports whether anyone did.

A queued `'cancel'` concerns the run, not the holder: it stays queued when the
key changes hands or is released, until some holder's renewal delivers it. A
queued `'drain'` concerns the current holder and is dropped with its lease.

Since 2.3 a holder can ask for acknowledged delivery:
`renew(lease, ttlMs, { acknowledge: true })` keeps a delivered `'cancel'`
queued, reports it on every later renewal and hands it to the next holder,
until the holder records it durably and calls `ack(lease, 'cancel')`. The
renewal reports what stays queued in `queued`. `ack` is fenced by the lease: it
returns `false` and removes nothing once the key changed hands. The memory,
SQLite, Postgres and Redis providers support both; a provider without `ack`
ignores the option and removes every signal it delivers, as in 2.2.

```ts
import { createInMemoryLeaseProvider } from '@deuz-sdk/core/ops';

const leases = createInMemoryLeaseProvider();
const lease = await leases.acquire({ key: 'report', owner: 'worker-1', ttlMs: 30_000 });
console.log(lease?.token); // 1
console.log(await leases.acquire({ key: 'report', owner: 'worker-2', ttlMs: 30_000 })); // undefined

await leases.signal('report', 'drain');
const renewal = await leases.renew(lease!, 30_000);
console.log(renewal.held && renewal.signals); // ['drain']
await leases.release(lease!);
```

The in-memory provider suits tests and single-process deployments; its leases
die with the process. Use the SQLite, Postgres or Redis provider when several
processes share runs.

## Swarm leases

Pass `lease` to `createSwarm`. The executor acquires `swarm:<scope, runId>`
before it creates or resumes a run and renews it every `ttlMs / 3` through
`deps.clock`. `ttlMs` defaults to 30 000 and `owner` to a generated ID per swarm
instance.

- `run` and `resume` reject with `SwarmLeaseError` code `'held'` while another
  executor holds the run. `resume` claims the lease before its resume commit.
- A claim collects the signals queued under the run's key. A `'cancel'` that
  an earlier holder never read goes into the resume commit, so the run is
  cancelled before anything is dispatched. A new run ignores whatever its key
  still queues, because that predates it.
- If a renewal reports the lease gone, the executor aborts its tasks and writes
  nothing more. Its `handle.result` rejects with `SwarmLeaseError` code
  `'lost'`. Task records stay as they were, and the next executor reconciles
  them as it would after a crash.
- A zombie can also learn it was replaced from its own write: after a takeover,
  its next commit fails the store's revision check, possibly before any
  heartbeat. On a `SwarmConflictError` the executor renews once, and
  `handle.result` rejects with `'lost'` when the lease is gone. A conflict with
  a writer that holds no lease, such as a process without the `lease` option,
  stays a `SwarmConflictError`.
- A renewal that throws, for example during a database outage, counts as lost
  only once the lease could have expired; until then the next beat retries.
- The lease is released when the executor stops, whatever the outcome.

`SwarmResumeOptions` accepts `expectedRevision` and `expectedStatus`. A resume
whose run moved on rejects with `SwarmConflictError` and changes nothing.

```ts
import { createAgent } from '@deuz-sdk/core/agent';
import { createMockModel } from '@deuz-sdk/core/testing';
import { createInMemoryLeaseProvider } from '@deuz-sdk/core/ops';
import { createInMemorySwarmStore, createSwarm, SwarmLeaseError } from '@deuz-sdk/core/swarm';

const worker = createAgent({ model: createMockModel({ responses: [{ text: 'done' }] }) });
const swarm = createSwarm({
  agents: { worker },
  store: createInMemorySwarmStore(),
  lease: { provider: createInMemoryLeaseProvider(), owner: 'worker-1', ttlMs: 15_000 },
});

const handle = await swarm.run({
  scope: 'tenant-a',
  runId: 'nightly',
  tasks: [{ id: 'answer', agent: 'worker', prompt: 'Answer.' }],
});
try {
  console.log((await handle.result).run.status);
} catch (error) {
  if (error instanceof SwarmLeaseError && error.code === 'lost') {
    // Another process took the run over; this one has stopped writing.
  } else throw error;
}
```

## Drain

`handle.drain()` stops new dispatch and waits for in-flight tasks to finish
normally. The run then settles `'suspended'` with its remaining tasks pending,
or reaches its terminal status if nothing remains. A `run.drained` event
precedes `run.settled`, and the lease is released, so a later `resume`
continues where the drain stopped. Use it for rolling deploys. `recover` takes
over only `'running'` runs, so resume drained runs explicitly, for example
from `listRuns({ status: 'suspended', limit })`; a run suspended on an approval
simply suspends again.

A `'drain'` lease signal does the same from another process: the executor
drains on its next heartbeat. The signal is meant for the current holder, so it
is dropped if the run changes hands or is released first.

## Cancellation from any process

`swarm.requestCancel(key)` reports what it did:

| Result | Meaning |
| --- | --- |
| `'signalled'` | This process drives the run and cancelled it, or the lease holder was sent `'cancel'`. The holder cancels on its next heartbeat or just before it settles. |
| `'recorded'` | Nobody drives the run. A compare-and-set commit stored `cancelRequested` and a `run.cancelled` event; the next executor cancels the run's pending work. |
| `'settled'` | The run already completed, became partial, or was cancelled. |

A signalled cancel is not lost when its holder stops first. If the holder
crashes before reading it, or the cancel arrives just after the holder's last
check and the run settles `'suspended'`, the `'cancel'` stays queued under the
run's key, and the next executor to claim the run cancels it before
dispatching anything.

Since 2.3 it is not lost after the holder reads it either. With a provider that
has `ack`, as the memory, SQLite, Postgres and Redis providers do, the executor renews
with acknowledged delivery: the cancel stays queued until the commit that
records it, or until the run's end makes it moot, and only then is it
acknowledged. A holder that reads the cancel and dies, or whose cancel commit
fails, leaves it for the next executor, even if its lease lapsed meanwhile.
With a provider without `ack`, the 2.2 behaviour applies: the holder queues a
cancel it failed to record again before it lets the lease go, which needs it to
still hold the key, and a process that dies between reading and recording the
cancel loses it.

A run that completed or became partial before the cancel reached it keeps its
status.

Without a lease provider, a request against a run that another process drives
is recorded, and that executor's next commit then fails its revision check.

## Recovery

`swarm.recover({ scope?, limit? })` lists `'running'` runs, which after a crash
have no live executor, and resumes each one this process does not drive with
`expectedRevision`. It resolves to `{ handles, failed }`: the executors it
started, and the runs it could not resume, each with its `key` and `error`.
Runs with a live lease holder, and runs that changed while being claimed, are
skipped silently. Any other failure is reported in `failed`. A run's own
failure, such as a run left by a worker with an older `definitionVersion` during
a rolling deploy, does not stop the call: the other runs are still recovered.
An outage does, because it would fail every run after it. If the lease provider
throws on an acquire, `recover` stops at once; after three failures in a row of
any other kind, such as a store that went down after the listing, it stops too.
Either way it returns the executors it already started, and `failed` ends with
the run that stopped it. `recover` needs the `lease` option and a store with the
`'list'` capability; the memory, SQLite, Postgres and Redis stores have it.

Heartbeats do not write to the swarm store, so a healthy run can keep an old
`updatedAt` and sort ahead of a crashed one. `recover` therefore pages through
the running runs, oldest `updatedAt` first, and examines up to 10 000 of them
per call; `limit` (1 to 1000, default 100) caps how many it takes over. Each
examined run costs one lease acquire: a run with a live holder is refused
before its snapshot is read. With more than 10 000 running runs, the ones past
that point wait until older runs finish.

The following complete example runs a worker process against one SQLite file.
Every process runs the same code; call `recover` at startup and on a timer.

```ts
import { createAgent } from '@deuz-sdk/core/agent';
import { createMockModel } from '@deuz-sdk/core/testing';
import { createSwarm } from '@deuz-sdk/core/swarm';
import { createSqliteSwarmStore } from '@deuz-sdk/core/swarm/sqlite';
import { createSqliteOpsStore } from '@deuz-sdk/core/ops/sqlite';

const path = './runs.sqlite';
const store = createSqliteSwarmStore({ path });
const ops = createSqliteOpsStore({ path });
const worker = createAgent({ model: createMockModel({ responses: [{ text: 'ok' }] }) });
const swarm = createSwarm({
  agents: { worker: { agent: worker, version: 'worker-v1' } },
  store,
  definitionVersion: 'jobs-v1',
  lease: { provider: ops.leases, ttlMs: 30_000 },
});

try {
  const { handles, failed } = await swarm.recover({ scope: 'tenant-a' });
  for (const { key, error } of failed) console.error('Cannot resume', key.runId, error);
  for (const handle of handles) console.log(handle.runId, (await handle.result).run.status);
} finally {
  await store.close();
  await ops.close();
}
```

`SwarmStore.listRuns({ status?, scope?, limit, after? })` is available directly
for dashboards; it orders runs by `updatedAt`, then scope and run ID. Pass the
last run of a page as `after` to get the runs strictly after it:

```ts
import { createInMemorySwarmStore } from '@deuz-sdk/core/swarm';
import type { SwarmRunRecord, SwarmStore } from '@deuz-sdk/core/swarm';

async function runningRuns(store: SwarmStore): Promise<SwarmRunRecord[]> {
  if (!store.listRuns) throw new Error('This store cannot list runs');
  const runs: SwarmRunRecord[] = [];
  let after: SwarmRunRecord | undefined;
  for (;;) {
    const page = await store.listRuns({ status: 'running', limit: 100, after });
    runs.push(...page);
    if (page.length < 100) return runs;
    after = page.at(-1);
  }
}

console.log((await runningRuns(createInMemorySwarmStore())).length); // 0
```

## Retention

The ops and swarm stores keep their rows until you prune them (2.3). Each
prune deletes only rows that nothing can still need and returns how many it
deleted; call them from a periodic job. Times are epoch milliseconds on the
store's clock: the injected `clock` for the memory and SQLite stores, the
database clock for Postgres, the server's `TIME` for Redis. Budget stores have
their own [`prune`](/docs/modules/budgets#retention).

| Call | Deletes | Keeps |
| --- | --- | --- |
| `leases.prune(before)` | Keys nobody holds: released, or expired before `before` | Held keys, and keys that queue a `'cancel'` for their run's next executor |
| `agentRuns.prune(before)` | Terminal native runs (completed, stopped or failed) last saved before `before` | Running, finalizing and suspended runs |
| `claims.prune(before)` | Claim keys granted before `before` | Newer keys |
| `prune({ before, scope?, limit? })` on a swarm store | Up to `limit` (1 to 1000, default 100) completed, partial or cancelled runs whose `updatedAt` is before `before`, oldest first, with their tasks, events and blackboard notes | Running and suspended runs |

`leases.prune` is part of `LeaseProvider` (optional, like `ack`), and
`prune` of `SwarmStore`; the memory, SQLite, Postgres and Redis implementations
have both. `agentRuns.prune` and `claims.prune` belong to the SQLite, Postgres
and Redis ops stores.

What a prune deletes is gone:

- The next holder of a pruned lease key starts again at token 1, and a holder
  whose lease expired before `before` finds it lost when it renews. Choose
  `before` well past any pause an executor could survive. A lease that has not
  expired yet is never pruned: a `before` later than the store's clock, such as
  a host clock running ahead of the database, is cut back to the store's time.
- A pruned agent run can no longer be resumed or inspected, and its run ID is
  free again.
- A pruned claim key can be claimed again. Keep every key that an occurrence or
  a delivery may still repeat: the scheduler's `lookbackMs` and catch-up
  window, and your webhook provider's retry period.
- A pruned swarm run can no longer be resumed, read or replayed, and its key is
  free again.

```ts
import { createSqliteOpsStore } from '@deuz-sdk/core/ops/sqlite';
import { createSqliteSwarmStore } from '@deuz-sdk/core/swarm/sqlite';

const day = 86_400_000;
const ops = createSqliteOpsStore({ path: './runs.sqlite' });
const swarms = createSqliteSwarmStore({ path: './runs.sqlite' });

try {
  const now = Date.now();
  const leases = await ops.leases.prune(now - day);
  const agentRuns = await ops.agentRuns.prune(now - 30 * day);
  const claims = await ops.claims.prune(now - 7 * day);
  // A swarm prune deletes a page of runs per call: repeat while a page is full.
  let swarmRuns = 0;
  for (;;) {
    const page = await swarms.prune({ before: now - 30 * day, limit: 100 });
    swarmRuns += page;
    if (page < 100) break;
  }
  console.log({ leases, agentRuns, claims, swarmRuns });
} finally {
  await swarms.close();
  await ops.close();
}
```

## SQLite ops store

`createSqliteOpsStore({ path, database?, wal?, clock? })` returns `leases`,
`agentRuns`, `claims` and `close()`. `claims` is a durable
[schedule claim](/docs/modules/schedule#durable-claims-from-the-ops-stores) for
`createScheduler` and `handleSignal`. The store keeps its own schema version
table and writes in `BEGIN IMMEDIATE` transactions or single statements, so
several processes can share the file, including the swarm store's file. Lease
times come from `clock`, which defaults to the host clock: processes sharing a
file must have synchronised clocks.

## Postgres

`createPostgresSwarmStore({ client, schema? })` and
`createPostgresOpsStore({ client, schema? })` take any client with
`query(sql, params)`, such as a `pg` pool; the ops store returns `leases`,
`agentRuns` and `claims`. The schema defaults to `public` and must exist; the
tables are created on first use, in one statement that queues on an advisory
lock, so several processes can start on a new schema at once.

```ts
import pg from 'pg';
import { createSwarm } from '@deuz-sdk/core/swarm';
import { createPostgresSwarmStore } from '@deuz-sdk/core/swarm/postgres';
import { createPostgresOpsStore } from '@deuz-sdk/core/ops/postgres';

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });
const ops = createPostgresOpsStore({ client: pool });
const swarm = createSwarm({
  agents: {},
  reducers: { total: { execute: () => 42 } },
  store: createPostgresSwarmStore({ client: pool }),
  lease: { provider: ops.leases },
});

const { handles, failed } = await swarm.recover();
console.log(`${handles.length} runs taken over, ${failed.length} could not be resumed`);
```

A pool may run consecutive queries on different connections, so the stores use
no client-side transactions. Every write is one SQL statement: a swarm commit
updates the run row only at the expected revision, and every task, channel and
event write in the same statement is gated on that update. If another writer
moved the run first, nothing is written and the commit rejects with
`SwarmConflictError`. Postgres leases use the database clock, so host clock skew
does not matter.

The stores are built for `READ COMMITTED`, Postgres's default, and also run
under a `REPEATABLE READ` or `SERIALIZABLE` session default. There a contended
write can fail with a serialization failure (40001), and any write can be
chosen as a deadlock victim (40P01). Postgres rolls such a statement back
whole, so since 2.3 every store sends it again, up to five attempts in all:

| Store | Writes that run again |
| --- | --- |
| Ops (`createPostgresOpsStore`) | Lease acquire, renew, release, signal and ack; agent run saves; claims and their release; every prune |
| Swarm (`createPostgresSwarmStore`) | Run creation, commits and prune |
| Budget (`createPostgresBudgetStore`) | Reserve, settle, release and prune |
| Store pack (`createPostgresStores`) | Memory, chat, session and run upserts, updates and deletes |

Table creation runs again on the same codes. When the attempts run out, a swarm
create or commit rejects with `SwarmConflictError`, whose `cause` is the driver
error, so `resume`, `recover` and `requestCancel` treat it like any other
conflict. Every other write rejects with the driver error, whose `code` is
`'40001'` or `'40P01'`; a budget admission reports it as `admission_failed`.
Each write's checks run inside its statement, so running it again cannot
double-apply it: a retried agent run save whose revision moved on is rejected as
a revision conflict, for example. Concurrency under `REPEATABLE READ` is
covered by tests that inject these failures, and by a suite that runs the
stores' contracts and races of concurrent writers on a real Postgres, through a
pool of several connections that all default to `REPEATABLE READ`. That suite
runs when `DEUZ_TEST_POSTGRES_URL` names a database, as in the repository's CI.

## Redis

`createRedisOpsStore({ client | url, prefix? })` (2.3) returns `leases`,
`agentRuns`, `claims` and `close()`, like the SQLite and Postgres ops stores.
The same entry has `createRedisBudgetStore`, the
[budget store](/docs/modules/budgets#durable-stores), and
`@deuz-sdk/core/swarm/redis` has `createRedisSwarmStore`, the swarm store. All
three are Node-only and need Redis 7 or later.

```ts
import { createClient } from 'redis';
import { createSwarm } from '@deuz-sdk/core/swarm';
import { createRedisSwarmStore } from '@deuz-sdk/core/swarm/redis';
import { createRedisOpsStore } from '@deuz-sdk/core/ops/redis';

const redis = createClient({ url: process.env.REDIS_URL });
await redis.connect();
const ops = createRedisOpsStore({ client: redis, prefix: 'jobs' });
const swarm = createSwarm({
  agents: {},
  reducers: { total: { execute: () => 42 } },
  store: createRedisSwarmStore({ client: redis, prefix: 'jobs' }),
  lease: { provider: ops.leases },
});

const { handles, failed } = await swarm.recover();
console.log(`${handles.length} runs taken over, ${failed.length} could not be resumed`);
```

- **One Lua script per operation.** Redis runs a script atomically, so a lease
  changes hands at most once, an agent run save is a compare-and-set on its
  revision, a claim key is granted once and a budget admission never admits
  past a limit. A swarm commit reads what its validation needs in one script
  and writes in another that runs only while the run is still at the revision
  and generation it read: a concurrent writer gets `SwarmConflictError` and
  nothing of its commit is written, and a run pruned and created again under the
  same key never takes a write meant for the old one. There is no `WATCH` or
  `MULTI`: on a shared node-redis connection a watch is not isolated from the
  other commands in flight, and an optimistic transaction needs a retry loop
  under contention.
- **Server time.** Lease expiry, claim and agent run times and budget windows
  come from Redis `TIME`, read inside the scripts, so host clock skew does not
  matter.
- **One hash tag per store.** Every key starts with `{<prefix>:ops}`,
  `{<prefix>:budget}` or `{<prefix>:swarm}` (the prefix defaults to `deuz`), so
  a Redis Cluster keeps each store in one slot, where every script stays atomic.
  A prefix holding `{` or `}` is refused.
- **Clients.** The stores need one method, `eval(script, { keys, arguments })`,
  node-redis's `EVAL` signature, typed `RedisScriptClient`. A connected
  node-redis client (v4, v5 or v6, standalone or cluster) fits as it is; wrap
  ioredis with `wrapIoredisClient(io)`. `{ url }` instead of `{ client }`
  imports the optional `redis` peer on first use and connects once; `close()`
  quits that connection and is final. An injected client is never closed.
- **Batched retention.** `leases.prune`, `agentRuns.prune`, `claims.prune` and
  the budget store's `prune` remove at most 1 000 entries per script and run
  again until a batch comes back short, so a large backlog never holds the
  server in one long script. A swarm prune deletes up to its `limit` in one
  script.
- **Durability is your server's.** Redis acknowledges a write from memory. What
  survives a crash depends on its persistence: with AOF and
  `appendfsync everysec` up to about a second of writes can be lost, and with
  snapshots alone everything since the last one. A replica promoted after a
  failover may lack the last writes it had not received. A lost lease write
  costs liveness, which the revision fence covers; a lost budget charge or
  agent run save is lost. Enable AOF for these stores.

| Key (tag `T`) | Holds |
| --- | --- |
| `T:lease:owner`, `T:lease:token`, `T:lease:signals` | Hashes by lease key |
| `T:lease:expiry` | Sorted set of lease keys by expiry, 0 once released |
| `T:run:payload`, `T:run:revision` | Hashes by native run ID |
| `T:run:terminal` | Sorted set of terminal native runs by their last save |
| `T:claims` | Sorted set of claim keys by the time they were granted; keys are stored as they are |
| `T:schema` | The layout version, one string per store |

The budget and swarm stores keep a hash per request, scope and run, with sorted
sets that index them; their key layouts are listed in the source of
`node/redis-budget.ts` and `node/swarm-redis.ts`. The stores' contracts run
offline against ioredis-mock, which runs the same Lua scripts, and against a
real Redis 7 in the repository's CI when `DEUZ_TEST_REDIS_URL` names one,
including races of concurrent writers on two connections.

## Schema versions and upgrades

Every durable store keeps its own schema version in a table of its own,
separate from the versions of the records it stores. A store refuses a schema
version newer than it reads, with an error such as `Unsupported Postgres ops
schema version 2; this build reads version 1`, so an older process never writes
through a newer layout.

| Store | Version table | Version in 2.2 and 2.3 |
| --- | --- | --- |
| SQLite swarm (`createSqliteSwarmStore`) | `deuz_swarm_schema` | 2. A 2.1 file (version 1) is upgraded in place on first open, and 2.1 then refuses it |
| Postgres swarm (`createPostgresSwarmStore`) | `deuz_swarm_pg_schema` | 1, the same layout as SQLite's 2 |
| SQLite and Postgres ops (`createSqliteOpsStore`, `createPostgresOpsStore`) | `deuz_ops_schema` | 1 |
| SQLite and Postgres budget (`createSqliteBudgetStore`, `createPostgresBudgetStore`) | `deuz_budget_schema` | 1 |
| SQLite evolve (`createSqlitePopulationStore`) | `deuz_evolve_schema` | 1 |
| Redis ops, budget and swarm (`createRedisOpsStore`, `createRedisBudgetStore`, `createRedisSwarmStore`) | the key `{<prefix>:<store>}:schema`, stamped on first use | 1 (new in 2.3) |
| Store packs (`createSqliteStores`, `createPostgresStores`) | `PRAGMA user_version`, `deuz_meta` | 1; see [Stores](/docs/modules/stores#migrations-and-schema-ownership) |

The records inside carry versions of their own:

| Record | Versions |
| --- | --- |
| Legacy loop checkpoint (`AgentCheckpoint.version`) | 1. Since 2.3, `deserializeCheckpoint` and `resumeFromCheckpoint` refuse any other version with `CheckpointVersionError` (code `checkpoint_version_unsupported`); a checkpoint without a version reads as 1 |
| Native run envelope (`AgentRunEnvelope.version`) | 1; a resume refuses any other, and since 2.3 also an envelope holding a loop or sub-agent checkpoint whose version is not 1 (`CheckpointVersionError`), before anything is written. Its `revision` is the write fence, not a format version |
| Swarm run (`SwarmRunRecord.version`) | 1 for a fixed DAG, 2 for a dynamic run (2.2), which 2.1 refuses |
| Execution snapshot (`ExecutionContextSnapshot.version`) | 1, or 2 when it carries persistent admission (2.2), which 2.1 refuses |
| Ledger snapshot (`BudgetLedgerSnapshot.version`) | 1, or 2 when it carries folded aggregates or persistent admission (2.2), which 2.1 refuses |

No store changes its schema version in 2.3. On first use the stores add only
objects that 2.2 ignores, so 2.2 and 2.3 processes can share a database during a
rolling deploy:

| Store | Added on first 2.3 use |
| --- | --- |
| SQLite and Postgres ops | Indexes `deuz_claims_claimed_at` and `deuz_agent_runs_updated_at` |
| SQLite and Postgres budget | Index `deuz_budget_requests_state`. SQLite also adds `deuz_budget_totals`, kept by three triggers on the history table, which 2.2 processes fire too, and fills it from the history |
| SQLite swarm | Index `deuz_swarm_runs_settled` |

Building an index blocks writes to its table until it is built. On a large
Postgres table, create the index beforehand without blocking writes, under the
same name in the store's schema, and the store finds it in place:

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS deuz_claims_claimed_at ON public.deuz_claims (claimed_at);
CREATE INDEX CONCURRENTLY IF NOT EXISTS deuz_agent_runs_updated_at ON public.deuz_agent_runs (updated_at);
CREATE INDEX CONCURRENTLY IF NOT EXISTS deuz_budget_requests_state ON public.deuz_budget_requests (state, created_at);
```

A later change that older builds cannot work with will raise a store's version.
The Postgres stores then upgrade a schema forward on first use: the steps from
its stored version to the current one run in order, followed by any new tables
and indexes, in the one statement that holds the store's advisory lock. A
failure leaves the schema as it was, and processes starting together upgrade it
once. Processes with an older build then refuse the schema, so upgrade every
process that shares it, and back the database up first if you may need to roll
back.

## Native agent run revisions

`AgentRunEnvelope.revision` increases by one on every save. The SQLite,
Postgres and Redis `agentRuns` stores, and `createInMemoryAgentRunStore`, reject any save
that is not the stored revision plus one. An envelope written by 2.1 has no
revision and counts as 0. An executor whose save is rejected stops, and its run
result reports the failure.

```ts
import { runAgent } from '@deuz-sdk/core/agent';
import { createMockModel } from '@deuz-sdk/core/testing';
import { createSqliteOpsStore } from '@deuz-sdk/core/ops/sqlite';

const ops = createSqliteOpsStore({ path: ':memory:' });
try {
  const result = await runAgent({
    model: createMockModel({ responses: [{ text: 'saved' }] }),
    prompt: 'Say something.',
    session: { store: ops.agentRuns, runId: 'agent-1', scope: 'tenant-a' },
  });
  console.log(result.status, (await ops.agentRuns.load('agent-1'))?.revision);
} finally {
  await ops.close();
}
```

Native runs have no lease of their own: the revision check already stops a
second executor from overwriting the first. Swarm tasks keep their agent state
inside the swarm run, which the swarm's lease and revision protect. Terminal
runs stay in the store until `agentRuns.prune` removes them; see
[Retention](#retention).
